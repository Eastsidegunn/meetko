# RFC 0001 — meetko 계약 0.1

2026-10-27 · 상태: 초안, 참조 구현과 테스트 통과

## 요약

계약은 세 문서와 하나의 프로토콜이다.

```
엔진 ──engine-result──▶ 코어 ──meeting-data──▶ 플러그인 ──plugin-output──▶ 코어 ──▶ GUI
                         (저장·버전·검증)          stdio JSON-RPC 2.0
```

| 문서 | 스키마 | 누가 쓰나 | 읽는 쪽의 태도 |
| --- | --- | --- | --- |
| engine-result | `contract/schemas/engine-result.schema.json` | 엔진 (채널 하나 단위) | 코어가 엄격하게 검사 |
| meeting-data | `contract/schemas/meeting-data.schema.json` | 코어 | 플러그인은 모르는 필드를 무시 |
| plugin-output | `contract/schemas/plugin-output.schema.json` | 플러그인 | 코어가 엄격하게 검사 (모르는 필드 거부) |

플러그인은 함수다: `plugin(meeting-data) → plugin-output`. 같은 입력에는 같은 출력을 내고, 상태가 없으며, 다른 플러그인을 모른다.

## 원시 재료와 거기서 나온 결정

`raw/`(로컬, 커밋하지 않음)에서 같은 회의 하나를 세 엔진으로 돌린 원시 출력을 보고 결정했다.

**녹음**: `tools/make_fixture.py`가 만든다. 마이크 채널(ch0)은 HiKE(Apache-2.0)의 실제 한영 혼용 발화 5개, 루프백 채널(ch1)은 macOS TTS 두 목소리의 대본 6개다. 69.4초이고, 0.8초 겹침과 4초 무음을 넣었다. 같은 입력이면 같은 오디오가 나오는 것을 확인했다.

**엔진**
- whisper.cpp 1.9.5 + large-v3-turbo: 배치 전사
- sherpa-onnx 2.0.1 한국어 스트리밍 zipformer: 라이브 전사
- sherpa-onnx pyannote+3D-Speaker: 화자 분리
- Silero VAD: 발화 구간

| 관찰 (원시 출력) | 계약에 준 영향 |
| --- | --- |

| 같은 파일을 같은 파라미터로 두 번 돌리면 whisper.cpp 출력이 바이트 단위로 같았다 | 설계 문서의 재현성 0.77은 다른 엔진(mlx_whisper 추정)의 값이다. whisper.cpp에서는 파라미터 고정만으로 재현된다. 버전 분리는 엔진 교체 때문에 여전히 필요하다 |
| 한국어 전용 스트리밍 모델이 영어 위주 발화에는 아무 텍스트도 내지 않았다(마이크 live CER 0.88) | `coverage`(전사를 시도한 구간)를 단어와 따로 둔다. 텍스트가 없다는 것은 발화가 없다는 뜻이 아니다 |
| sherpa 스트리밍 토큰 시각은 세그먼트 기준 상대 시각이고, 세그먼트 시작 시각은 따로 준다 | 엔진은 자기 오디오 기준 ms로 보고한다. 회의 타임라인으로의 변환은 코어가 한다 |
| 스트리밍 partial이 이 모델에서는 덧붙이기만 했다 | 다른 엔진은 다시 쓴다. 그래서 계약은 덧붙이기가 아니라 revision 단위 교체로 정한다 |
| 화자 분리가 두 TTS 목소리를 한 화자로 합쳤다(DER 0.40) | 화자 분리 품질은 계약 문제가 아니다. 대신 화자 구간이 단어와 별도로 계약에 있어야 비교가 가능하다(아래) |
| 라이브 토큰 지연: p50 0.38초, p95 0.50초. 100ms 청크당 계산은 약 6ms | 1초 이하 목표 범위 안이다. 이벤트에 `emitted_at_ms`를 두어 지연을 잴 수 있게 한다 |

## 불변 규칙

### 시간
- 모든 시각은 **녹음 시작 기준 정수 밀리초**다. 부동소수 초를 쓰지 않는다. 이전 프로토타입은 float 초를 소수 3자리로 반올림해 저장했다.
- 구간은 `[start_ms, end_ms]`이고 `start ≤ end`다. 길이 0인 단어를 허용한다(DTW 시점).
- 타임라인은 회의마다 **하나**다. 채널마다 시간 기준을 따로 두면 채널 간 비교가 불가능해진다. 이전 프로토타입이 실제로 이 문제에 걸렸다.
- 엔진은 자기가 받은 오디오 기준으로 보고한다. 채널 오프셋은 코어가 더한다.
- 엔진이 녹음 끝을 넘는 시각을 보고하면 코어가 녹음 길이로 자른다. 녹음이 기준이다. 이 규칙은 속성 테스트가 찾았다.

### 식별자
- 단어·화자·턴 id는 **한 버전 안에서만** 의미가 있다. 재전사하면 단어가 달라지므로, 버전 간 id 안정성은 약속하지 않는다. 이전 프로토타입도 같은 결론이었다.
- 화자 id도 버전 안에서만 유효하다. 다른 버전의 `s1`은 다른 사람일 수 있다. 사람 이름과의 연결은 사용자 데이터이고 코어가 관리한다.

### 앵커 (플러그인 결과 → 전사)
- 앵커는 입력 버전 안의 **단어 범위** `{from, to}`다. 단어 순서상 `from ≤ to`이고 양 끝을 포함한다.
- 플러그인은 시각을 만들지 않는다. 시각은 코어가 단어로부터 계산한다(`core.resolve`). 플러그인이 지어낸 시각이 화면에 나가는 일을 막는다.
- 요약·액션아이템·표의 모든 항목에는 근거 앵커가 1개 이상 필요하다. "기록의 신뢰"를 스키마가 강제하는 부분이다.
- 버전이 바뀌면 결과는 stale이 된다. 새 버전에 근거를 다시 붙이는 일은 코어의 저장 계층이 한다. 방식은 W3C Web Annotation처럼, 버전(State) + 단어 범위 + 시각 범위 + 인용문을 함께 저장하는 쪽이 유력하다. 플러그인 계약에는 포함하지 않는다.

### 턴
- 턴은 단어 순서상 이어지는, 같은 채널·같은 화자의 단어들이다. 2000ms 이상 쉬면 턴이 끊긴다. 쉼 규칙은 플러그인 결과가 실제로 뭉치는 것을 보고 넣었다.
- 턴은 편의를 위한 뷰다. 단어가 정본이다.

### 화자
- 채널이 화자를 정하는 경우(마이크): `basis = "channel"`이고 모든 단어가 그 화자다. 발화 구간은 VAD에서 온다. VAD를 "라벨 하나짜리 화자 분리"로 취급해서 새 갈래를 만들지 않았다.
- 화자 분리가 정하는 경우: 단어 길이의 절반 이상을 정확히 한 화자가 덮을 때만 그 화자를 붙인다. 아니면 `ambiguous`나 `unassigned`로 둔다. 이전 프로토타입의 규칙과 같다.
- `speaker_spans`는 단어와 별도로 둔다. 단어별 화자만으로는 화자 분리 결과를 복원할 수 없어서, 표준 채점기(DER)로 비교가 불가능했기 때문이다. 이 필드는 왕복 시험이 요구해서 추가했다.
- 처음에는 화자 분리가 없는 채널의 화자 구간을 coverage로 채웠다. 그러자 발언 시간이 녹음 전체(69.4초)로 나왔다. coverage는 발화가 아니다.

### 출처 (버전마다)
`version.producers[]`에 role(asr / diarization / alignment / edit), 엔진 id와 버전, 모델 id와 sha256, 실제 파라미터, `word_timing`, `granularity`, `network`, 채널을 남긴다. 원본 오디오는 `recording.sha256`으로 남긴다. 엔진 결과에는 채널 오디오의 `audio_sha256`이 들어간다.

### 진화
- 코어 → 플러그인: **관대한 읽기**. 플러그인은 모르는 필드를 무시해야 한다. 적합성 테스트가 모르는 필드를 주입해도 결과가 바뀌지 않는지 확인한다.
- 플러그인/엔진 → 코어: **엄격한 검사**. 모르는 필드, 모르는 표시 타입, 없는 단어를 가리키는 앵커는 모두 거부한다(이전 프로토타입에서 가져온 fail closed).
- 마이너 버전 안에서는 필드 추가만 한다. 표시 타입은 늘릴 수는 있어도 줄이지 않는다.
- 계약 버전은 `initialize`에서 협상한다. 호스트가 지원 목록을 보내면 플러그인이 하나를 고른다(LSP의 positionEncoding 협상 방식).

### 텍스트
UTF-8을 쓴다. 단어 텍스트에는 공백과 제어 문자를 허용하지 않는다(스키마 pattern). 라벨과 제목에는 제어 문자를 허용하지 않는다. 단어 하나로 CTM 열이나 WebVTT cue를 쪼개거나 주입하지 못하게 하기 위해서다(보안 리뷰, 2026-10-27 추가). 스트리밍 unit은 새 단어의 시작을 알리는 앞 공백 하나만 허용한다. 문자 오프셋은 계약 어디에도 두지 않는다. LSP는 UTF-16 오프셋을 기본으로 두었다가 3.17에서 인코딩 협상을 추가해야 했다. 단어 id를 쓰면 이 문제가 처음부터 생기지 않는다.

### 실패
- 플러그인은 전부 아니면 전무다. 부분 결과는 없다. 실패는 JSON-RPC error로 알린다.
  - −32001: 지원하지 않는 계약
  - −32010: 입력 처리 실패
  - −32601: 없는 메서드
  - −32800(취소)은 LSP에서 빌려 예약만 했다.
- 결과가 비어 있는 것은 실패가 아니다(`items: []`).

## 프로토콜 0.1

- 전송: 플러그인 프로세스의 stdin/stdout에 **줄 단위 JSON-RPC 2.0**(NDJSON)을 쓴다. stderr는 로그다. JSON 직렬화에는 줄바꿈 문자가 날것으로 들어가지 않으므로 LSP의 Content-Length 헤더가 필요 없다.
- 순서는 `initialize {contract: ["0.1"]}` → `{contract, plugin, outputs}`, 이어서 `run {input}` → plugin-output을 필요한 만큼 반복하고, 마지막에 `shutdown` → null 후 종료한다.
- 요청은 한 번에 하나만 보낸다. 서버 모드(WebSocket)는 같은 메시지를 다른 전송으로 보낸다(미구현).
- 매니페스트의 `run.command`는 배열이다. 셸을 거치지 않는다.

| 출처 | 빌린 것 | 버린 것 |
| --- | --- | --- |

| W3C Web Annotation | 버전(State) + 여러 선택자로 앵커를 견고하게 만드는 방식. 코어 저장 계층에 쓴다 | 플러그인에 선택자 여러 개를 요구하는 것 |
| LSP | initialize 협상, JSON-RPC 2.0, 취소 코드, 인코딩 문제에서 얻은 교훈 | Content-Length 프레이밍 |
| 이전 내부 프로토타입 | fail closed, 근거 앵커 필수, 화자 세대 개념, 50% 덮임 규칙, `python -S`로 도는 의존성 없는 플러그인, 표시 타입 화이트리스트 | 채널별 시간 기준, float 초, 세그먼트 id 앵커(재처리하면 깨짐), ASR 출처 미기록 |

Praat TextGrid와 ELAN의 원문은 이번에 직접 열지 않았다. 표의 해당 행은 알려진 형식 지식을 근거로 했다. W3C Web Annotation과 LSP 3.17은 원문의 해당 절을 확인했다.

## 검증 결과

모두 `raw/`가 있는 로컬에서 재현할 수 있다. 우리 판단이 아니라 외부 도구와 독립 구현으로 확인했다.

**1. 손실 없음**: 원시 엔진 출력과 계약 데이터에서 내보낸 CTM/텍스트·RTTM을 같은 서드파티 채점기에 넣었다. 점수가 모든 행에서 같았다(`tools/score.py`).

| | 원시 | 계약 경유 |
| --- | --- | --- |
| CER draft 마이크 (jiwer) | 0.2278 | 0.2278 |
| CER draft 루프백 | 0.4757 | 0.4757 |
| CER live 마이크 | 0.8790 | 0.8790 |
| CER live 루프백 | 0.6486 | 0.6486 |
| DER 루프백, collar 0 (pyannote.metrics) | 0.4042 | 0.4042 |

**2. 엔진을 바꿔도 플러그인이 그대로 돈다**: whisper.cpp로 만든 draft와 sherpa-onnx로 만든 live에서, 두 플러그인이 수정 없이 돌았다.

**3. 두 언어 독립 구현**: Python(표준 라이브러리만, `-I -S`)과 Rust(serde_json만)로 만든 플러그인이 같은 적합성 테스트를 통과했다. 모르는 필드를 주입해도 결과가 같았고, 같은 입력을 다시 넣어도 결과가 같았다(함수성).

**4. 속성 테스트**: hypothesis가 임의의 엔진 출력(단어, 화자 구간)을 만들어 코어에 넣고, 불변 규칙 I1~I9가 항상 성립하는지 확인한다. 녹음 끝을 넘는 구간 결함을 이 테스트가 찾았다.

**5. 거부 테스트**: 모르는 필드, 다른 버전용 결과, 없는 단어, 뒤집힌 범위, 없는 화자, 빈 근거, 임의 HTML을 코어가 모두 거부한다.

`pytest tests` 결과: 26 통과.

**아직 없는 외부 증거**
- 외부 개발자가 스펙만 보고 플러그인을 만들어 본 기록이 없다. 가장 강한 증거인데 아직 없다.
- 클라우드 ASR 엔진으로 엔진 교체를 시험하지 않았다. 비용이 들고 데이터가 밖으로 나가므로 승인이 필요하다.
- 실제 회의 녹음은 쓰지 않았다. 실제 한영 혼용 발화를 배치한 합성 회의다.

## 고려했다가 버린 대안

- **세그먼트를 정본으로 두기**: whisper 세그먼트가 두 화자를 합치고, 엔진마다 세그먼트 경계가 다르다. 단어를 정본으로 둔다.
- **플러그인이 시각으로 앵커하기**: 플러그인이 지어낸 시각을 검증할 방법이 없다. 단어 id를 쓰면 존재 여부를 검사할 수 있다.
- **버전 간 안정적인 단어 id**: 재전사하면 단어 자체가 달라져 약속할 수 없다. 버전에 묶고, 재매핑은 코어가 한다.
- **`oneOf` 표시 타입 스키마**: 잘못된 항목에 "어느 스키마에도 맞지 않음"만 보여줬다. `type` 분기(`if/then`)로 바꾸자, 무엇이 잘못됐는지(예: 빈 근거)를 알려준다. 외부 개발자 경험 문제라서 바꿨다.
- **VAD를 여섯 번째 갈래로 두기**: 라벨 하나짜리 화자 분리로 충분하다. 갈래를 늘리지 않는다.
- **Content-Length 프레이밍(LSP)**: NDJSON으로 충분하고, 아무 언어로나 더 쉽게 구현할 수 있다.

## 미결정

- **오디오 권한 경로**: 오디오를 받는 플러그인에 녹음을 어떻게 건넬지(파일 경로, 스트림).
- **시간 예산**: 참조 호스트에는 타임아웃이 없다. 응답하지 않는 플러그인이 호스트를 막는다.
- **서버 모드 전송**: WebSocket, 그리고 엔진 스트리밍을 위한 오디오 전송.
- **버전 간 앵커 재매핑 알고리즘**: 코어 저장 계층의 일이다.
- **한영 혼용 채점 지표**: CER은 음차("review"→"리뷰")를 오류로 센다. 루프백 CER 0.48의 상당 부분이 음차다. HiKE의 MER·PIER와 외래어 라벨을 써야 한다.
- **TTS 음성의 재배포 가능 여부**: macOS 시스템 음성 출력을 재배포해도 되는지 확인하지 않았다. 그래서 오디오는 커밋하지 않고, 생성 스크립트만 커밋한다.
- **사용자 설정을 함수 입력에 넣을지**: 예를 들어 요약 템플릿 선택이다.
